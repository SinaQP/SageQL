Open-source Python SDK · Persian and English

Text-to-SQL, without letting the model write SQL.

SageQL lets managers ask for reports in Persian or English. A language model only chooses from what the host registered; deterministic code checks permissions, writes parameterized SQL and runs it read-only. A wrong or manipulated model can produce a wrong report, never an unauthorized query.

What changes when the model doesn't write SQL

Model-written SQLSageQL
Who writes the queryThe modelSageQL's compiler, from registered IDs
JoinsChosen by the modelOnly relationships the host registered
Row and tenant filtersRequested in the prompt, or checked afterwardsAdded to every query from the authenticated user
What the model seesTable and column names, often sample rowsBusiness labels and IDs; never rows, SQL or physical names
When the model is wrong or manipulatedA wrong or unauthorized query can runA wrong report at worst; anything unregistered is rejected before SQL exists

How a request becomes a report

  1. ModelExtract intent Picks registered measures, groupings, period and filters by ID, or asks a question.
  2. SageQLValidate Every ID must be registered and allowed for this user. Anything else is rejected.
  3. SageQLResolve Dates, Solar Hijri months and product names are resolved locally.
  4. SageQLCompile Writes the SQL with the user's row policy and bound parameters.
  5. SageQLExecute Read-only, with row, time and work limits. Rows never go back to the model.

    Why I built it

    In July 2026 I built QuerySmith: a language model wrote T-SQL for SQL Server, and a guard checked it. It allowed one SELECT, no comments or extra statements, only columns inside a scope, plus access profiles and result masking. Each protection meant recognizing one more pattern in SQL the model had invented.

    In September I started SageQL by inverting that design. The model never writes SQL. It picks registered concepts by ID, and SageQL compiles the query itself, so tenant filters, joins and limits come from code instead of from text a model produced. The question changed from "is this SQL safe?" to "is this a report the host allowed?", which is much easier to answer exactly.

    The reports I had in mind are the ones managers ask for in Persian, with Solar Hijri dates, so Persian is the default and the calendar is resolved locally rather than by the model.

    Limitations and next steps

    • The benchmark is small. 27 scored synthetic reports; results vary by about ±2 reports between runs.
    • Understanding still fails sometimes. The model can drop a filter or pick the wrong period or limit. Every report states its interpretation, so a user can catch it.
    • Only registered operations. No arbitrary formulas, share-of-total or model-chosen joins yet; those requests are declined rather than approximated.
    • SQL Server is compiled and checked offline, but not yet tested end to end against a live server in CI; SQLite runs every test.
    • Authentication belongs to the host. SageQL enforces the policy it is given.

    Next: letting users correct an interpretation in one click, a library of verified questions, more report operations, and a larger public evaluation. Roadmap.
